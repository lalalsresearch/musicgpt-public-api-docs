**Complete Preprocess Audio Upload** verifies an uploaded file and pre-processes it for the feature it's headed to.

Use this instead of [Complete Audio Upload](/api-documentation/endpoint/upload-audio-complete) when you know what the file is for. It runs the same verification, then starts whatever work that feature can do before the request arrives, and reports how far that work has got.

<Info>
  Today the one pre-processing step is remix acceleration: the file is pushed to a generation account straight away, so a later `POST /Remix` starts from a clip the backend already holds instead of transferring it again — that's what makes the remix start streaming sooner. The route is named for the shape of the work rather than for that one feature, so other features can hang their own pre-processing off it without a second endpoint.
</Info>

The call returns immediately with the phase acceleration is currently in. Poll it to watch the run advance; `ready` is the phase that never changes again, and it ends the poll.

<Note>
  Idempotent: repeating this call returns the current phase and never accelerates the file twice.
</Note>

---

## Endpoint

```http
POST /api/public/v2/upload_audio/{upload_id}/complete/pre-process
```

## Try It Yourself

Use the [Upload Endpoint Explorer](/api-documentation/endpoint/upload-audio-complete-preprocess) to check or poll acceleration status.

## What comes back

`status` is the lifecycle you poll on: `processing` while the run is still moving, `completed` once it's stopped. `phase` is the leg behind it:

- `pending` — queued, not started
- `uploading` — the file is on its way to the generation account
- `transcribing` — the backend is inferring lyrics and metadata from it
- `ready` — terminal, and the only phase you're ever left holding

<Warning>
  There is deliberately no failure phase. Every way acceleration can stop short — the run reported failure, a requested wait ran out, or the file was never eligible for acceleration in the first place — reports `completed` / `ready`, because all of them leave you in the same position: holding a verified `upload_id` that `POST /Remix` accepts. Acceleration only changes how fast the next request starts, never whether it works, so a failure of it isn't a failure you have anything to do about.
</Warning>

`ready` therefore means "this upload is usable," not "a clip is waiting." The one observable difference is `lyrics`: a run that actually finished carries the transcript, and a run that stopped short comes back with `lyrics` empty. Don't branch on that — an instrumental also transcribes to nothing.

### Waiting instead of polling

Pass `wait_seconds` (0–60) to have the API hold the request until acceleration settles, for when one call is easier than a loop. The request returns as soon as the run settles, however it settles — the wait is a ceiling, not a delay. Don't combine it with a tight poll loop; each call would then block for the whole window.

If the wait runs out, you get `ready` with empty `lyrics` rather than being held any longer — acceleration is usually seconds from done at that point, and `POST /Remix` waits for it again on its own side.

### Acceleration never changes the outcome

`POST /Remix` works identically whichever phase you got, including no acceleration at all: the generation worker still owns the full download-and-upload path and falls back to it. So there's no error to handle here — a 200 means the `upload_id` is verified and usable, and `status` is information about latency, not validity. You can fire `POST /Remix` at any phase; waiting for `ready` buys a faster start, not a different result.

## Path Parameters

| Parameter    | Type   | Required | Description                                                                 |
| ------------ | ------ | -------- | ----------------------------------------------------------------------------- |
| `upload_id`  | String | Required | The identifier returned by `POST /upload_audio`. Must reference a single audio file; a zip dataset handle has nothing to accelerate. |

## Query Parameters

| Parameter      | Type    | Required | Default | Description                                                                 |
| -------------- | ------- | -------- | ------- | ------------------------------------------------------------------------------ |
| `wait_seconds` | Integer | Optional | 0       | Seconds to hold the request while acceleration finishes, 0–60. Defaults to 0, which answers immediately. |

---

## Returns

A `Complete_Preprocess_Audio_Upload_Response` object:

| Field                | Type    | Description                                                                                                                                |
| -------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `success`            | Boolean | Whether the upload passed verification                                                                                                    |
| `message`            | String  | A descriptive status message                                                                                                               |
| `upload_id`          | String  | The verified upload identifier. Pass this to `POST /Remix` (v2).                                                                          |
| `status`             | String  | `processing` or `completed`                                                                                                                |
| `phase`              | String  | The leg the accelerated upload is on. Never reports a failure; every terminal outcome is `ready`.                                          |
| `lyrics`             | String  | Lyrics transcribed from the audio. Empty unless `phase` is `ready`, and still empty for an unfinished `ready`, an instrumental, or a transcript too short to be one. |
| `expires_in_seconds` | Integer | How long the upload stays referenceable                                                                                                    |

## Example: polling

One call every few seconds:

```json
{"status": "processing", "phase": "pending",      "lyrics": ""}
{"status": "processing", "phase": "uploading",    "lyrics": ""}
{"status": "processing", "phase": "transcribing", "lyrics": ""}
{"status": "completed",  "phase": "ready",        "lyrics": "I drive the long..."}
```

---

## Sample Request (Python)

```python
import requests

upload_id = "upl_x7Kd2mQ..."
url = f"https://api.musicgpt.com/api/public/v2/upload_audio/{upload_id}/complete/pre-process"

headers = {"Authorization": "<API_KEY>"}
params = {"wait_seconds": 15}

response = requests.post(url, headers=headers, params=params)
print(response.json())
```

## Sample Response

```json
{
  "success": true,
  "message": "Upload ready",
  "upload_id": "upl_x7Kd2mQ...",
  "status": "completed",
  "phase": "ready",
  "lyrics": "I drive the long way home...",
  "expires_in_seconds": 86400
}
```

## Errors

| Status | Code                   | Meaning                                                          |
| ------ | ---------------------- | --------------------------------------------------------------------- |
| 400    | `BAD_REQUEST`           | Malformed `upload_id` or no file uploaded yet                        |
| 404    | `RESOURCE_NOT_FOUND`    | Upload doesn't exist, has expired, or belongs to another customer    |
| 422    | `UNPROCESSABLE_CONTENT` | Stored object doesn't match size, type, or checksum, or isn't audio  |
| 429    | `TOO_MANY_REQUESTS`     | Rate limit exceeded                                                  |
| 424    | `FAILED_DEPENDENCY`     | Upload could not be verified                                         |
| 401    | `UNAUTHORIZED_ACCESS`   | Missing or invalid API key                                           |
